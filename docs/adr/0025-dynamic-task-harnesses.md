# ADR 0025 — Dynamic Task Harnesses Are Declarative and Runtime-Mediated

## Status

Proposed

## Context

Reusable Harness Packs give NAVI skills durable loop limits, soft graph policy,
and verifier recipes. They cannot cover every open request in advance. A capable
agent should be able to derive task-specific acceptance claims and verification
strategy from user intent, repository context, and project conventions.

Giving the model arbitrary hook code would undermine NAVI's security and
portability guarantees. It could create a vacuous verifier, bypass approvals,
enable an MCP server, or gain access beyond the current session. NAVI also has
two distinct `VerifierSpec` definitions today: an executable command runner in
`navi-core::verifier` and a descriptive recipe type in `harness_pack`.

## Decision

### 1. A dynamic task harness is declarative, ephemeral, and scoped to a task

The agent may propose a `DynamicTaskHarness` associated with one task contract.
It declares claims, verifier references, scheduling triggers, evidence policy,
budget hints, and recovery hints. It is persisted with session state, not
written to the project tree.

It is not an arbitrary program and is not a new general-purpose scripting
language. Reusable author-created Harness Packs remain the mechanism for
durable, shareable workflow policy under `{data_dir}/harnesses/`.

### 2. The runtime validates every proposed harness

The engine validates schema, claim/evidence compatibility, verifier identity,
resource limits, security policy, and references before activation. A dynamic
harness may narrow authority but never widen it:

- no new tools, paths, approvals, network access, plugins, or MCP connections;
- no direct write to verification state or completion state;
- no project-local NAVI bookkeeping;
- no executable native extension code; third-party extension remains WASM-only;
- commands run only through the existing command/security/approval path.

Model-proposed command verifiers must use registered templates or receive the
same review and approval treatment as a model `run` action. A command such as
`echo ok` is not accepted as evidence for an unrelated behaviour claim merely
because it exits successfully.

### 3. Consolidate verifier representation before dynamic harness execution

NAVI will introduce one canonical, serializable verification specification and
result/evidence model. It must be able to describe built-in, command, browser,
plugin, and future external verifiers without erasing the security boundary.

`navi-core::verifier::VerifierSpec` and
`navi-core::harness_pack::types::VerifierSpec` will migrate to that model via
compatibility adapters where necessary. No dynamic harness execution lands while
two competing verifier semantics exist.

### 4. Verifier output is bounded, redacted, and attributed

Verifier output becomes model feedback and session data. It must observe the
same secret-redaction and bounded-observation rules as tool output. The runtime
records verifier identity, configuration provenance, execution environment,
workspace fingerprint, result, and diagnostics.

## Consequences

### Positive

- NAVI can convert new, informal tasks into progressively verifiable work.
- The model can express domain-specific intent without inventing an unsafe hook
  runtime.
- Harness Packs and task-local harnesses share one verifier foundation.
- Security, approval, and plugin policy stay inside `navi-core`.

### Negative

- The schema and validator are new critical engine surfaces.
- Some proposed claims cannot be meaningfully verified with available tools;
  the harness must record them as inconclusive or escalate rather than pretend.
- Canonicalizing verifier types requires a careful compatibility migration.

## Alternatives considered

| Alternative | Why rejected |
| --- | --- |
| One static harness per domain | Cannot cover arbitrary repositories and open requests. |
| Arbitrary Python or shell hooks generated by the model | Violates the WASM-only extension boundary and is unsafe to trust. |
| Treat any successful shell command as a verifier | Does not establish that the command covers the claimed property. |
| Keep pack recipes and executable verifier specs separate indefinitely | Creates divergent semantics and prevents reliable completion contracts. |
